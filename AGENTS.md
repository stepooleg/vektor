# AGENTS.md — Инструкции для агента и разработчиков Vektor

> Этот файл описывает договорённости, принципы и правила работы в репозитории
> корпоративного HR-приложения **Vektor**. Читать всем (людям и агентам) перед началом работы.

---

## 1. Что такое Vektor

**Vektor** — корпоративное HR-приложение для:

- сбора обратной связи (в т.ч. оценка 360°);
- периодической оценки персонала (360°, самооценка, матрица компетенций);
- автоматического формирования индивидуальных планов развития (ИПР);
- обучения во встроенном LMS;
- непрерывной обратной связи и портфолио достижений;
- аналитики для HR и руководства.

- **Спецификация продукта:** [`SPEC.md`](./SPEC.md)
- **Брендбук и дизайн-токены:** [`BRANDBOOK.md`](./BRANDBOOK.md)
- **Дорожная карта по фазам:** [Milestones](https://github.com/stepooleg/vektor/milestones)
- **Список задач:** [Issues](https://github.com/stepooleg/vektor/issues)

> Документы-источники (`SPEC.md`, `BRANDBOOK.md`) **не редактируются агентом** без явного
> запроса пользователя. Это контролируемые документы заказчика.

## 2. Главный приоритет — качество

«Максимальное качество — приоритет». Сроки не ограничены (SPEC §16).
Поэтому:

1. **Не торопимся за счёт пропусков.** Лучше меньше, но сделанное до конца.
2. **Никаких «и так сойдёт».** Если знаешь лучший способ — используй его.
3. **Каждая фаза — поставляемая.** В конце фазы приложение собирается, тесты зелёные,
   документация актуальна.
4. **Чистый код, читаемость, предсказуемость.** Код пишется один раз, читается много раз.

## 3. Принцип разработки: Test-First (TDD)

**Сначала тесты, затем реализация.** Без исключений.

Процесс для каждой задачи (issue):

1. **Понять задачу.** Прочитать связанный раздел SPEC и существующий код.
2. **Написать тест(ы)**, описывающий ожидаемое поведение (красный).
   - Backend: `pytest` (`backend/tests/`).
   - Frontend: `Vitest` + `React Testing Library` (`frontend/src/**/*.test.tsx`).
   - E2E (позже): Playwright.
3. **Запустить тест** — убедиться, что он падает по правильной причине.
4. **Написать минимальную реализацию**, чтобы тест стал зелёным.
5. **Рефакторинг** без изменения поведения (тесты должны оставаться зелёными).
6. **Проверить:** `pytest`, `ruff`, `mypy` / `npm test`, `lint`, `typecheck` — всё зелёное.
7. **Коммит** с понятным сообщением, ссылка на issue (`Closes #N` или `Refs #N`).

> PR без тестов к новой функциональности **не принимается**.
> Тесты покрывают и бизнес-логику, и важные крайние случаи (анонимность, права, просрочки).

## 6. Правила коммитов и веток

### 6.1. Ветвление

- `main` — всегда собирается, тесты зелёные, демо работает.
- Работа ведётся в ветках `feature/<краткое-имя>` или `fix/<...>`,
  в идеале с номером issue: `feature/IDP-12-autobuild`.
- PR в `main` обязателен. CI должен быть зелёным.

### 6.2. Сообщения коммитов (Conventional Commits, на русском допустимо)

```
feat(assessment): добавлен расчёт агрегатов цикла 360°

Учитывается порог анонимности (минимум N оценщиков в группе).
Без группы нужного размера результат не возвращается.

Refs #14
```

- Префиксы: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `ci`, `perf`, `style`.
- Scope — домен (`assessment`, `lms`, `idp`, `users`, `analytics`, …).
- Закрывать issue в коммите: `Closes #N` (PR merge в `main`).

### 6.3. Не коммитить

- Секретов, ключей, `.env`, паролей, токенов.
- Личных данных (реальных сотрудников).
- Сгенерированных артефактов (`dist/`, `__pycache__/`, `.venv/`, `node_modules/`).
- Дампов БД.

## 7. Кодстайл

### 7.1. Backend (Python)

- `ruff` для импортов/стиля, `ruff format` для форматирования.
- `mypy --strict` для типизации (постепенный строгий режим).
- Имена: `snake_case` для функций/переменных, `PascalCase` для классов,
  `UPPER_SNAKE` для констант.
- Докстринги (Google-style) для публичных функций/классов.
- Никакой бизнес-логики в views — только в services/слое домена.

### 7.2. Frontend (TypeScript)

- `strict: true` в `tsconfig.json`.
- Функциональные компоненты + хуки.
- `ESLint` + `Prettier`.
- Имена: `PascalCase` компоненты, `camelCase` функции/переменные.
- **Никаких хардкод-цветов** — только дизайн-токены (BRANDBOOK §8.2).

## 8. Дизайн и UI — следуем брендбуку

Все визуальные решения — из [`BRANDBOOK.md`](./BRANDBOOK.md):

- **Цвета** — только через CSS-токены (`--color-primary`, `--bg-surface`, …).
  Хардкод HEX в компонентах запрещён.
- **Темы** — светлая и тёмная равноправны. Проверять все экраны в обеих.
- **Шрифт** — Ubuntu (дефолт), Roboto (альтернатива). Без смешивания.
- **Анимация** — токены длительности/easing; уважать `prefers-reduced-motion`.
- **Иконки** — линейные 1.5px (Lucide).
- **Доступность** — контраст AA/AAA, фокус-стили, размеры касаний.
- **Тон голоса** — уважительный, ясный, поддерживающий (BRANDBOOK §9).

Чек-лист соответствия: BRANDBOOK §10.2.

## 9. Безопасность (критично — ПДн, 152-ФЗ)

Приложение обрабатывает персональные данные сотрудников (SPEC §12).
Соблюдать **строго**:

- **Анонимность 360°** — сырые ответы оценщиков недоступны никому, кроме audit-log.
  HR/руководитель видят только агрегаты с учётом порога (SPEC §6.3).
- **RBAC + принцип минимума привилегий** (SPEC §2).
- **Хеширование паролей** — Argon2.
- **TLS 1.2+** для всего трафика; шифрование БД и бэкапов at rest.
- **Audit log** для всех действий над чувствительными данными (SPEC §12.3).
- Секреты — только через env-переменные, никогда в коде.
- Не логировать ПДн и сырые оценки.

> При любом изменении, затрагивающем оценки/права/аудит, — добавить/обновить тесты
> на анонимность и права доступа.

## 10. Definition of Done (DoD) для issue

Задача считается выполненной, когда:

- [ ] Написаны тесты **до** реализации и они зелёные.
- [ ] Бизнес-логика реализована по SPEC/BRANDBOOK.
- [ ] Линтинг и типизация зелёные (`ruff`, `mypy`, `eslint`, `tsc`).
- [ ] CI зелёный.
- [ ] Для UI — проверено в светлой и тёмной темах, на accessibility.
- [ ] Документация/докстринги обновлены.
- [ ] Если затронуты права/анонимность/ПДн — покрыто тестами и описано в PR.
- [ ] PR прошёл ревью, issue закрыта ссылкой на коммит/PR.

## 11. Как агент работает над задачей

1. Прочитать этот файл и связанный раздел SPEC/BRANDBOOK.
2. Уточнить непонятное у пользователя (через AskUserQuestion), не гадать.
3. План реализации — через EnterPlanMode для нетривиальных задач.
4. **Сначала тесты** → красный → реализация → зелёный → рефакторинг.
5. Прогнать локально `pytest`/`npm test`, линтеры, типизацию.
6. Коммит с осмысленным сообщением и ссылкой на issue.
7. Сообщить пользователю итог: что сделано, что проверено, что осталось.

### Не делать без явного разрешения пользователя

- Пушить в `main` напрямую (только через PR).
- Менять `SPEC.md` / `BRANDBOOK.md`.
- Удалять или переписывать чужой код без необходимости.
- Публиковать репозиторий/менять видимость.
- Менять CI/настройки безопасности.
- Коммитить секреты.
- Выполнять разрушительные операции над БД/продом.

```bash

npm ci
```
