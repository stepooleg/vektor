# ADR 0003. Модульная монолитная архитектура

- **Дата:** 2026-08-06
- **Статус:** Принято
- **Основание:** SPEC.md §11.2 (Архитектура)

## Контекст

Нагрузка — до 500 активных пользователей, пиковая до 200 одновременных (SPEC §11.3).
Это умеренный масштаб, не требующий микросервисов. При этом доменов много
(оценка, обучение, ИПР, аналитика, интеграции), и нужна чёткая разделённость.

## Решение

**Модульный монолит**: единое Django-приложение с доменными приложениями (apps) внутри:

```
backend/apps/
  users/         orgstructure/   competencies/
  assessment/    feedback/       portfolio/
  lms/           idp/            analytics/
  notifications/ audit/
```

Принципы:

- Каждое app — отдельный домен со своими моделями, сервисами, API.
- Связь между доменами — через сервисные функции/события, не через прямые SQL-joins
  по чужим моделям.
- Асинхронные задачи (рассылки, синхронизация с 1С, расчёт агрегатов) — в Celery (background workers).
- API-first: DRF предоставляет REST API (`/api/v1/...`), frontend — отдельное SPA/PWA.

## Последствия

- Простота развёртывания и отладки on-premise (один процесс + воркеры).
- Домены изолированы, можно в будущем вынести в сервисы при росте.
- Чёткие границы обязывают соблюдать дисциплину зависимостей между apps.

## Альтернативы

- **Микросервисы с первого дня** — отклонены: избыточная операционная сложность для 500 пользователей.
- **FastAPI + событийная архитектура** — отклонена по ADR 0002.
